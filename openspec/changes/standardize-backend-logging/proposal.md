# Proposal：统一后端结构化日志

## 背景

后端已经依赖 `structlog 26.1.0`，并在请求上下文和全局异常处理中写入日志，但当前实现仍存在以下问题：

- 业务 `structlog` 使用 `PrintLoggerFactory`，Uvicorn、标准库和第三方库日志没有进入同一渲染链路。
- 日志级别写死为 `INFO`，无法按环境配置。
- Uvicorn access log 与项目请求中间件可能重复记录同一次请求。
- 请求中间件与全局异常处理器可能对同一未知异常重复记录 ERROR。
- 客户端 `X-Request-ID` 被原样接受，缺少长度和字符约束。
- 当前异常日志会包含原始异常消息；结构化字段也没有统一的递归脱敏兜底。
- 现有测试只验证错误响应不泄密，没有验证日志 schema、上下文隔离、脱敏或标准库日志接管。

## 目标

- 继续使用现有 `structlog`，统一业务、Uvicorn、标准库与第三方库日志的处理和输出格式。
- 建立稳定的结构化日志字段、事件命名和请求上下文契约。
- 通过配置控制日志级别，同时保留本地 console 与部署 JSON 两种输出。
- 让每个请求只有一条完成日志，让每个未知异常只有一条 ERROR 日志。
- 对外部 `request_id`、异常信息和结构化字段实施安全边界，禁止凭据和用户业务正文进入日志。
- 为请求、异常、依赖探测和标准库互操作补齐自动化验证。

## 范围

- `core.logging` 的统一配置、logger 获取、上下文绑定和安全处理能力。
- `LOG_LEVEL` 运行配置及既有 `LOG_FORMAT` 的统一行为。
- 请求上下文、请求完成日志、未知异常日志和 `X-Request-ID` 校验。
- PostgreSQL、Redis、RustFS 就绪探测失败日志。
- Uvicorn access/error 与标准库日志接入策略。
- 后端日志相关测试、环境变量示例、工程文档与后端 AI Coding 规则。

## 非目标

- 不更换为 Loguru，不并存第二套日志框架。
- 不封装与 `debug/info/warning/error` 同名的转发函数，不为尚不存在的业务事件预建专用 helper。
- 不引入日志采集平台、OpenTelemetry、分布式 trace、指标、告警、日志持久化或轮转方案。
- 不记录请求体、请求头、query string、SQL、模型输入输出或用户业务正文。
- 不为健康探针引入状态转换、限流或告警抑制状态机。
- 不修改前端、OpenAPI 契约或外部 PostgreSQL、Redis、RustFS 的运行状态。
- 不执行 Next.js build、Docker image build、Git commit 或 push。

## 风险

- 接管标准库日志可能改变 Uvicorn 和第三方库的输出格式；通过 ProcessorFormatter 集成测试验证。
- 外部库自由文本无法仅凭字段名完全判断敏感内容；默认限制第三方日志级别，并对常见敏感键和文本模式做兜底脱敏。
- 关闭 Uvicorn access log 后，请求日志完全依赖项目中间件；必须覆盖成功、4xx 和 5xx 路径。
- 去除异常原始消息会降低部分排障信息；以异常类型、安全堆栈位置、事件上下文和 `request_id` 补偿。
- 健康探针持续失败时会重复产生 warning；首期接受该行为，出现真实噪声后再单独设计抑制机制。

## 验收证据

- Ruff、mypy 和完整后端 pytest 的实际执行结果。
- JSON 日志可解析且稳定字段完整的测试结果。
- console/JSON 和可配置级别行为测试结果。
- 并发请求 `request_id` 隔离、非法外部 ID 替换和上下文清理测试结果。
- 标准库日志与业务日志共享渲染格式、Uvicorn access log 不重复的测试结果。
- 敏感字段递归脱敏、安全异常堆栈和未知异常只记录一次 ERROR 的测试结果。
- 就绪探测失败只记录安全技术元数据的测试结果。
