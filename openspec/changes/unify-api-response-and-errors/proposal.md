# Proposal：统一 API 响应与异常处理

## 背景

后端已经具备 RFC 9457 Problem Details 处理雏形，但当前仍存在以下不一致：

- 业务成功响应尚无统一模型，未来路由容易形成不同的返回结构。
- Starlette 路由层产生的 404、405 未被现有处理器转换。
- 参数校验错误只有数量，没有可供前端定位字段的结构化信息。
- 异常响应模型未进入 OpenAPI，生成客户端无法获得错误契约。
- `HTTPException` 携带的认证等响应头未被透传。

## 目标

- 为业务 API 建立显式、可生成 OpenAPI 的统一成功响应模型。
- 建立项目状态码枚举与项目异常体系，统一转换为 RFC 9457 响应。
- 让前端稳定读取数字 `code`、`message`、`data`，并在需要时读取 `error_key`。
- 覆盖项目异常、框架 HTTP 异常、参数校验异常和未知异常。
- 通过测试与契约生成验证真实行为。

## 范围

- 后端状态码、成功响应、分页响应和 Problem Details 模型。
- 全局异常处理器及必要的响应头透传。
- 404、405、422、500 等典型场景测试。
- OpenAPI 导出及前端生成 client 同步。

## 非目标

- 不实现认证或其他业务模块。
- 不改变 `/health/live`、`/health/ready` 的裸响应结构与状态语义。
- 不使用中间件自动包装文件、流式响应或无正文响应。
- 不运行 Next.js build、Docker build，不启动或变更外部依赖。

## 风险

- RFC 9457 标准字段与前端通用字段存在语义重复；通过固定映射和模型测试防止漂移。
- 自动包装可能使 OpenAPI 失真；本变更只提供显式泛型响应模型与创建函数。
- 错误详情可能泄露内部信息；未知异常始终对外脱敏，校验错误不返回原始输入或内部上下文。

## 验收证据

- Ruff、mypy、pytest 的实际执行结果。
- OpenAPI 中成功响应和 Problem Details schema 的生成结果。
- 前端生成 client 与 OpenAPI 一致性检查结果。
- 404、405、422、项目异常、未知异常和响应头透传测试结果。
