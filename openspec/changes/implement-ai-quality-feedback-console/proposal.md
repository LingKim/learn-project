# Proposal：实现 AI 质量反馈与管理员诊断台

## 背景

项目已经规划文档解析、混合检索和 Rerank，也将为每次检索生成 `trace_id`。但如果用户只能点击“无帮助”，管理员只能看到聚合错误或最终结果，就无法判断问题来自解析/索引、关键词召回、向量召回、融合、Rerank、证据门禁还是后续生成与引用。

同时，既有产品边界明确禁止管理员自由查看用户资料和业务正文。质量排查必须以用户主动反馈为入口，以单次请求、最小字段、明确目的和可撤销授权为边界，不能把“客服排障”变成管理员浏览用户知识库的旁路。

## 目标

- 在 AI 结果组件提供统一“我要反馈”入口，自动绑定 `trace_id`、业务类型和结果引用。
- 使用结构化问题类型、描述、期望结果和明确授权形成可跟踪的质量工单。
- 为用户提供工单状态、补充说明、授权管理、管理员回复和解决结论。
- 为管理员提供质量概览、工单队列、工单详情、链路诊断、隔离回放、内部协作和公开回复。
- 通过限定快照、追加授权、到期/撤销、访问审计和禁止导出维持用户隐私边界。
- 让同一能力未来复用于资料问答、出题、评分、转写、简历分析和面试复盘，不只绑定当前 RAG 检索。

## 依赖

- 依赖 `implement-document-parsing-indexing` 交付 `RetrievalTrace`、不可变检索策略版本和消融 runner。
- 第一个面向普通用户的真实入口依赖后续资料问答结果页；在问答页交付前，可以先完成领域模型、权限、API 和管理员诊断台的合成 Trace 验证，但不得制作无法绑定真实结果的假反馈按钮。
- 继续复用现有双 JWT 角色鉴权、`ApiResponse`/`PageResponse`、RFC 9457、审计能力和前端 API/Query 访问链路。

## 非目标

- 不允许管理员自由搜索或浏览用户会话、知识库、文件、原始录音或其他业务正文。
- 不支持工单附件、聊天式在线客服、外部联系方式、退款、赔偿或 SLA 商业承诺。
- 不在诊断页直接修改、发布或回滚提示词、模型与检索策略。
- 不自动根据单个用户反馈修改全局策略，也不把管理员标记“已解决”等同于模型质量已经改善。
- 不建设 MCP、完整 RetrievalOps 平台或跨系统工单集成。

## 成功标准

- 任一支持的 AI 结果都能以一个有效 `trace_id` 创建且只创建一个幂等反馈工单，返回稳定工单号。
- 用户明确看到授权字段和用途；未授权、已撤销、已过期或跨工单访问均为 0 成功结果并产生审计。
- 管理员能从工单内判断故障阶段、查看允许范围的快照并运行不影响线上结果的消融回放。
- 管理员不能下载原文件、导出用户正文、进入用户知识库或查看同一会话其他内容。
- 用户可以查看处理进度、补充信息、撤销授权并收到管理员公开回复；内部备注绝不返回用户端。
- 自动化覆盖状态机、幂等、授权、越权、撤销竞态、回放隔离、正文日志和前端访问边界。

## 风险

- 授权文案不清可能形成无效同意；必须逐项列出字段、目的和有效期，不能使用默认勾选或笼统“同意隐私协议”。
- Trace 或工单可能成为用户正文旁路；快照需加密、范围固定、限时、审计并与普通日志/指标隔离。
- 单条反馈不代表普遍质量问题；管理员结论必须区分个案、已复现缺陷和评测集回归。
- 回放若复用线上写路径可能污染索引或改变策略；必须使用只读、隔离 runner。
- 用户可能提交提示词注入、辱骂或敏感凭据；反馈内容按不可信输入处理并限制展示、搜索、长度和频率。
